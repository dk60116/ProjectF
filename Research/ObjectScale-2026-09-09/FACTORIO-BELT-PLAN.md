# 팩토리오 벨트 방식 대조 및 적용 계획

2026-09-09 · ProjectF `b8aa85a` · 계획 문서

이전 최적화는 유효하며 유지한다. 다만 현재 적용 범위는 **라인 조회 캐시, 전송 검증 통합, GPU 입력 재사용, 할당 감소**다. 팩토리오의 핵심인 **운송 라인이 아이템 간격을 소유하고 내부 이동의 반복 작업량을 줄이는 구조**까지 적용된 것은 아니다. 다음 목표는 캐시를 더 추가하는 것에서 나아가, 매번 갱신해야 하는 상태 자체를 줄이는 것이다.

이번에는 공식 자료 조사, 현재 코드 대조, 엔진을 사용하지 않는 기존 하네스 4개 재실행을 수행했다. 게임 코드·설정은 변경하지 않았으며 게임·Unity·라이브 프로파일러는 실행하거나 조작하지 않았다. 이 계획은 10만 개의 활성 공장 오브젝트라는 앞선 규모 문제를 염두에 두되, 벨트 개선만으로 전체 게임 60FPS를 보장하지 않는다.

### 부분 적용 또는 부족한 부분

**1. 라인은 실행 묶음이고, 아이템의 실제 소유자는 여전히 블록 슬롯이다.**

[BlockRuntimeSimulationState.ConveyorLaneStorage](<C:/Git/ProjectF/FactorioProject/Assets/Scripts/Map/Block.SimulationState.cs:138>)는 블록별 ItemIds·MoveFrames·MotionStates·PickupGateStates·MovementHoldUntilTimes를 보관한다. ConveyorLine에는 라인 단위 아이템 간격 저장소가 없다.

[직선 라인 이동 루프](<C:/Git/ProjectF/FactorioProject/Assets/Scripts/Map/TerrainGenerator.Conveyors.cs:3373>)는 wake 범위의 블록을 뒤에서 앞으로 순회하고, 블록 사이 및 같은 블록 안의 슬롯 전송을 호출한다. 그 앞뒤에도 retry work·runtime blocker·no-move 완료 검사가 있다. 조회 캐시가 적중해도 순회와 슬롯 상태 변경은 남는다. 항상 월드 전체를 도는 것은 아니지만 비용은 처리 범위 길이에 의존한다.

**2. 수면과 이벤트 기반 재개의 기반은 있지만 불필요한 재확인 경로가 남아 있다.**

- [no-move 이후 fallback](<C:/Git/ProjectF/FactorioProject/Assets/Scripts/Map/TerrainGenerator.Conveyors.cs:3117>)이 재시도 가능한 범위를 다시 direct wake로 보낼 수 있다.
- [fallback 조건](<C:/Git/ProjectF/FactorioProject/Assets/Scripts/Map/TerrainGenerator.Conveyors.cs:3335>)은 ShouldTickActiveConveyor가 false여도 아이템이 있으면 통과할 수 있다. [direct wake](<C:/Git/ProjectF/FactorioProject/Assets/Scripts/Map/TerrainGenerator.Conveyors.cs:777>)는 직선 retry를 지우며, 소비 단계에서 주변 이동 대기를 해제하는 경로가 있다.
- [WakeConveyorNetwork](<C:/Git/ProjectF/FactorioProject/Assets/Scripts/Map/TerrainGenerator.Conveyors.cs:2088>)의 지연 분기는 queueWake 인자를 저장하지 않고, [flush](<C:/Git/ProjectF/FactorioProject/Assets/Scripts/Map/TerrainGenerator.Conveyors.cs:626>)는 큐 등록을 수행한다. 요청 의도가 보존되지 않는 점은 현재 코드로 확인된다. 실제 총비용 중 비중은 추가 계측이 필요하다.
- 라인 wake는 대기 중 범위를 병합하지만 이미 처리된 라인인지의 판정은 소비 단계에도 있다. 이를 enqueue에서 바로 defer하는 변경은 큐 예산·다른 라인의 실행 시점을 바꿀 수 있어 단순 캐시 개선처럼 취급하면 안 된다.

과거 측정에서는 wake queue가 주요 벨트 비용이었다. 현재 최적화 이후의 실제 비용 비율은 다시 측정해야 한다.

**3. 긴 운송 구간으로 묶을 수 있는 범위가 제한적이다.**

[IsRuntimeConveyorLineBlock / IsStraightConveyorLineSuccessor](<C:/Git/ProjectF/FactorioProject/Assets/Scripts/Map/TerrainGenerator.Conveyors.cs:3887>)는 코너를 제외하고 같은 흐름 방향을 요구한다. 코너는 별도 그룹이며 cycle은 직선 fast path에서 제외된다. 경로가 휘어도 같은 속도로 흐를 수 있는 구간까지 하나의 시뮬레이션 데이터로 통합된 상태는 아니다.

단, ProjectF의 1F/2F·T자·분배기·혼합 속도·착지 대기는 고유한 규칙이다. 무조건 긴 라인으로 합치는 것은 목표가 아니다.

**4. 변경 한 곳이 큰 범위의 캐시 갱신으로 번질 수 있다.**

[EnsureConveyorLineCache](<C:/Git/ProjectF/FactorioProject/Assets/Scripts/Map/TerrainGenerator.Conveyors.cs:3715>)는 dirty 시 전체 라인/코너 캐시를 비우고 loadedBlocks를 다시 조사한다. 프록시 바인딩 변경도 저장소 범위에서 캐시를 보수적으로 무효화한다. 이는 정상 상태의 안전성을 확보한 대신 대규모 배치·탐험 변경에 추가 비용을 만든다.

[아이템 렌더 집합 변경](<C:/Git/ProjectF/FactorioProject/Assets/Scripts/Map/PortableItemRenderer.cs:795>)은 전체 활성 목록을 복사하고, [reconciliation](<C:/Git/ProjectF/FactorioProject/Assets/Scripts/Map/PortableItemRenderer.cs:863>)은 전체 캐시와 활성 목록을 조사한다. GPU 입력 캐시가 있어도 이 CPU 작업은 남는다.

**5. 벨트 시뮬레이션 그룹 병렬화는 미적용이다.**

[ConveyorItemTransformJobProcessor](<C:/Git/ProjectF/FactorioProject/Assets/Scripts/Rendering/ConveyorItemTransformJobProcessor.cs:19>)의 Job은 렌더 행렬 계산이다. 아이템 소유권·전송·wake 스케줄러 자체의 병렬화가 아니다. 현재 Block/Unity 객체 접근과 공유 알림을 그대로 worker로 옮기는 계획은 부적절하다.

## 구현 진행 상황

2026-09-09 후속 구현에서 효과가 없었던 점유 인덱스를 제거하고, 동일 속도 직선 내부 구간의 실제 라인 소유권·공통 이동량·정체 압축을 도입했다. 지원 구간은 기존 블록별 retry/blocker/이동 처리도 우회한다. 코너·2F·순환 등은 기존 backend와의 경계로 남는다. 적용 범위와 하네스 결과는 [구현 기록](LINE-GAP-IMPLEMENTATION.md)에 정리했다.

## 단계별 구현 계획

### 0단계 — 동작 계약과 프레임 전체 재현 경로 확보

**첫 구현 작업으로 권장한다.** 현재 하네스의 실제 메서드 추출을 활용하되, 프레임 순서와 처리 예산까지 연결하는 `Tools/ConveyorSchedulerHarness`를 추가한다. 특정 메서드만 비교하는 기존 wake 하네스와 역할을 구분한다.

기록할 관측값은 아이템 수량·ID·순서, 입출력 시점, 현재 보이는 위치, 집기 가능 시점, hold/착지 완료, 같은 프레임 중복 이동 방지, 막힘 해제 후 재개 시점이다. 내부 배열 배치나 새 저장소의 버전 숫자는 같을 필요가 없지만 외부 조회의 최신성·게임 동작은 같아야 한다. 기존 소규모 캐시 변경 하네스의 엄격한 비교는 그대로 유지한다.

메트릭은 wake 요청 원인·병합·실제 실행·no-move·fallback·예산으로 인한 대기, 라인/슬롯 방문 수, 오래된 대기 시간, 실물/가상 아이템 수, 라인 길이 분포, 렌더 전체 재조사 횟수다. 매 사건의 문자열 로그 대신 재사용 가능한 카운터/제한된 trace 버퍼를 사용한다.

검사 시계는 30/60/120FPS에 해당하는 deltaTime 및 불규칙 프레임, 정지/재개를 재현한다. 이 작업에 60Hz 고정 틱 전환을 섞지 않는다. 현재 시간 계약은 [ConveyorMotionTiming](<C:/Git/ProjectF/FactorioProject/Assets/Scripts/Map/ConveyorMotionTiming.cs:7>)을 기준으로 한다.

완료 조건: 동일 사건 스크립트의 결과가 재실행마다 같고, 실제 scheduler의 예산·재삽입·처리 순서가 검사에 포함되어야 한다. 전체 게임 메인 루프 동등성까지 확보했다고 주장하지 않는다.

### 1단계 — 현재 저장 구조에서 불필요한 wake와 렌더 재조사 축소

작은 변경 단위로 진행한다.

1. 지연 network wake에 queueWake 의도를 보존한다. 동일 대상의 true/false는 true 우선 OR 병합하고 처리 중 재진입을 확인한다.
2. 기존 retry·ready-delay·blocked waiter에 맞춰 요청을 분류한다. 실제 빈칸 발생·투입 완료·구조 변경과 단순 재확인을 구분해, 재확인이 이유 없이 주변 대기를 초기화하지 않게 한다. 같은 의미의 새로운 sleep 상태 배열은 추가하지 않는다.
3. no-move fallback은 실패 원인과 실제 진행 가능 시점을 근거로 좁힌다. 같은 프레임 wake 합치기는 0단계의 순서/공정성 검사 후 별도 변경으로 진행한다. 단순히 모두 다음 프레임으로 밀지 않는다.
4. 아이템 렌더 활성 집합을 추가/삭제된 handle 중심으로 갱신한다. 초기 로드·전체 재설정만 전체 reconciliation을 사용한다. 변경 목록의 용량과 삭제 후 재사용되는 handle 세대까지 관리한다.

완료 조건: 안정된 정체 구간에 외부 사건이 없을 때 반복 슬롯 처리와 재시도가 크게 줄고, 중간 한 개 회수/로봇팔 투입 직후 재개가 기준보다 늦어지지 않는다. 워밍업 후 반복 구간의 할당 증가가 없어야 한다.

Safety Scan이나 프레임당 512건 제한만 낮춰 개선으로 보고하지 않는다. 초기 단계에서는 누락 감시용 안전 스캔을 유지하고, 이후 정상 wake 경로가 입증된 범위에서만 축소한다. 이 단계는 현재 병목을 줄이는 작업이며 간격 저장 전환을 대체하지 않는다.

### 2단계 — 라인 소유권과 간격 기반 이동을 실제 경로에 도입

변경 범위는 크지만 10만 규모를 위한 핵심 단계다. 제안 위치는 `Assets/Scripts/Map/Conveyors/`, namespace는 `ProjectF.Conveyors`다. 파일 이름은 책임 확정 후 정하며 Block.cs에 두 번째 이동 시스템을 계속 덧붙이지 않는다.

**첫 대상:** 같은 속도·같은 이동 규칙을 가진 비순환 직선 데이터 아이템 구간. 분배기·합류·코너·hold/착지·실물 PortableObject·중간 상호작용은 초기에는 명시적인 구간 경계로 둔다. 모든 직선을 하나의 무조건 동일한 흐름으로 가정하지 않는다.

구현 순서:

1. Block 슬롯의 읽기/삽입/회수/이동준비 조회를 얇은 접근 경계로 모은다. 처음에는 기존 저장소에 위임하고 직접 배열 접근 호출부를 조사·축소한다.
2. 라인이 아이템 순서와 간격, 양 끝 여유, 이동 기준 시각/속도, 압축 진행 위치를 소유하게 한다. 루프 이동·삭제마다 전체 List를 앞당기지 않는 재사용 저장 구조를 선택한다. 동일 상대 운동으로 묶을 수 없는 아이템은 별도 경계/구간으로 분리한다.
3. 내부 진행은 구간의 이동량/간격 상태를 갱신한다. 외부 전송·집기·투입·관찰 대상 경계는 필요한 시점에 사건으로 처리한다. 블록 좌표 조회는 라인 상태에서 계산한다.
4. GPU 렌더 입력은 라인의 현재 상태와 경로에서 만든다. 화면 밖 라인의 논리를 멈추지 않고, 기존 컬링·입력 캐시를 재사용한다.

가장 중요한 완료 조건은 **라인 데이터를 추가한 뒤 기존 블록 배열을 매 프레임 다시 채우지 않는 것**이다. 그렇게 하면 원본이 두 개가 되고 작업량 감소도 사라진다. 지원 구간은 라인이 유일한 변경 가능한 소유자이며, 기존 블록 API는 조회/명령 경계가 된다. 미지원 구간은 명시적으로 기존 backend가 소유하고, 경계를 건널 때 한 번만 전송한다.

내부 슬롯 경계마다 기존 occupancy version과 dirty를 전부 쓰면 목표가 무너진다. 캐시 무효화와 이벤트 구독을 라인·상호작용 지점 기준으로 바꾸고, 조회 결과의 정확성을 테스트한다. 관측되지 않는 내부 알림까지 동일하게 재생하는 것은 계약에서 분리한다. 슬롯 선점·같은 프레임 이동 제한·pickup gate의 관측 동작은 보존해야 한다.

세이브는 첫 버전에서 기존 슬롯 스냅샷으로 **저장 시에만** 변환하는 방법을 우선 검토한다. 이동 시간·간격·gate·소유권을 손실 없이 표현할 수 없다면 저장 버전을 명시적으로 올린다. 호환 포맷을 억지로 유지해 동작을 잃지 않는다. 로드 시 라인 재분할이 달라도 동일 운반 상태가 복원되어야 한다.

성능 완료 조건: 관찰자와 외부 전송이 없는 동일 속도 자유 흐름 구간에서, 길이 100/1,000/10,000 증가에 따라 매 tick 아이템·블록 갱신 횟수가 선형 증가하지 않아야 한다. 막힘 압축의 포인터 이동은 반복 전수 검색 없이 누적 작업량으로 검사한다. 렌더·최초 생성·저장·삽입·회수 비용은 이 조건과 별도로 측정한다.

기존 전송과의 게임 동작 차이가 확인되면 지원 조건을 좁히고 원인을 해결한다. 이동 지연이나 간격 변화가 남아 있는 상태에서 전면 교체하지 않는다. 예전 미연결 `ConveyorRunStore.cs`를 복구하는 방식 대신, 이 단계의 산출물이 실제 직선 운반 경로를 통과하도록 한다.

### 3단계 — 로봇팔 상호작용과 구간 변경의 국소화

로봇팔은 지정된 집기/놓기 구간의 사건을 구독하고, 대상 아이템 추적 위치를 재사용한다. 현재 '주변에 대상이 있다' 또는 '놓는 곳이 벨트다'라는 이유로 수면을 막는 조건을 구체적인 입력/공간 변화 알림으로 대체할 수 있는지 검증한다. 팔의 논리 각도·완료 시각과 Transform을 분리하고, 렌더 데이터 준비 이전에 공간 컬링을 적용한다.

레이아웃 변경은 영향받은 라인의 이전/새 구간만 분할·병합한다. 라인 ID+세대, 대기자, 아이템 핸들, 렌더 소유자, 저장 조회가 함께 이관되어야 한다. 오래된 예약 사건은 세대 검사로 무효화한다. 전역 라인 캐시를 매번 비우는 경로를 축소한다.

동일 프레임에 팔이 회수하고 다른 팔이 투입하는 경우, 라인 분할 직전/직후 회수, 풀 재사용·청크 재생성, 플레이어 수동 회수와 자동 회수 경합을 포함한다. 스냅샷 조회 때문에 라인 전체를 매번 탐색하지 않는지 방문 수를 함께 확인한다.

### 4단계 — 코너·2F·합류·분배기·순환 확장 및 기존 코드 제거

먼저 경로 길이를 따라 진행하는 동일 속도 코너를 연결한다. 이어 2F와 합류를 추가하되 실제 높이·진행 방향·슬롯 규칙·점유 타이밍을 보존한다. 속도 차이·분배기·상호작용 노드는 명시적인 전송 경계로 유지하고, 가능한 구간만 합친다. 순환은 마지막에 다룬다.

각 지원 범위가 검증될 때마다 중복 fallback, 해당 범위에서 불필요해진 per-slot 모션/retry 배열, 오래된 캐시를 제거한다. 미지원 기능의 정상 경로는 유지하되 동일 구간에 두 소유자를 두지 않는다. 기존 구현은 차등 검증용 대역/기준 코드로만 남길 수 있다.

전체 기능이 새 backend로 넘어간 후에는 불필요한 전환 플래그·레거시 adapter도 제거한다. 최종 런타임 구조에 사용되지 않는 압축 저장소나 임시 우회 분기를 남기지 않는다.

### 5단계 — 병렬화는 남은 비용을 측정한 뒤 선택

라인 단위 단일 스레드 처리 후에도 시뮬레이션이 주요 병목이고 독립 그룹이 충분할 때 진행한다. Worker는 순수 데이터만 변경하고 Unity 객체를 직접 접근하지 않는다. 공유 팔·전력·인벤토리·wake·dirty 효과는 모아 안정된 그룹/사건 순서로 메인 스레드에서 반영한다.

그룹이 새로 연결되면 다음 병렬 실행 전에 합치고, 분리는 성능상 필요에 따라 나중에 수행할 수 있게 설계한다. 전송 경계만 분리했다고 전력 등 공유 상태까지 독립인 것은 아니다. 단일/복수 worker 수와 반복 실행에서 같은 상태 해시·출력 순서가 나오는지 검사한다. Job 입력 복사·완료 대기·그룹 관리 비용까지 포함해 채택 여부를 판단한다.

| 수명/저장 | handle 세대 변경, 풀 반환·재생성, 청크 재생성, 월드 초기화, 이동/정체 중 저장·복원 |

항상 아이템 보존·순서·집기 가능 시점·실제 처리량을 먼저 판정한다. FPS가 올라가도 운반이 늦어지면 통과가 아니다. 순수 커널의 자유 흐름 작업량은 활성 구간 수와 사건 수에 가까워져야 하며, 외부 관찰/변경에 필요한 작업까지 상수 시간이라고 주장하지 않는다.

엔진 없이 가능한 검증은 실제 C# 메서드/커널 차등 검사, 사건 trace, 방문 수, 워밍업 후 할당이다. 향후 사용자 지시로 게임 실행 검증을 진행할 때는 같은 빌드·세이브·카메라·시간 조건에서 CPU/GPU, p95/p99, 실제 운반량, 큐 최장 대기, 진단 켬/끔을 비교한다. 현재 요청에는 엔진 실행이 포함되지 않는다.

이 결과는 .NET 관리형 하네스의 실제 메서드와 대역 경계에서 확인한 것이다. Unity/IL2CPP 전체 컴파일, GPU 드라이버 내부 업로드, 현재 빌드 FPS 또는 전체 게임 동작의 완전한 동등성을 검증한 것은 아니다. 특히 wake 하네스는 프레임 전체 예산·fairness를 대체하지 않으므로 0단계 보강이 필요하다.

우선 착수 범위는 **0단계 사건/프레임 재현 하네스 → 1단계 wake 의도 보존과 정체 재시도 정리 → 2단계 실제 직선 구간의 라인 소유권 전환**으로 정한다. 로봇팔·시각 캐시 개선은 이 경계 설계와 연결하고, 멀티스레딩은 뒤로 둔다.
