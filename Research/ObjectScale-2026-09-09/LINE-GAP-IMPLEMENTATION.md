# 라인 소유권과 공통 이동 처리 — 2026-09-09

이전 점유 슬롯 간격 인덱스는 실제 효과가 없다는 사용자 피드백에 따라 제거했다. 이번 구현은 **동일 속도·동일 간격의 직선 내부 구간이 아이템 ID, pickup gate, 순서, 위치를 직접 소유**한다. 채택할 때 기존 슬롯에서 상태를 한 번 가져오고 ID·모션 슬롯을 비운다. 내부 이동 시 블록 배열을 다시 채우지 않는다. `TickActiveConveyors`에서 자동으로 실행되며 별도의 실험 플래그는 없다.

## 이동과 연결

- `ConveyorTransportStore<T>`: 배열 기반 treap에 정렬 좌표와 공통 변위를 저장한다. 공통 변위 아래 좌표 차이가 아이템 간격을 표현한다. 자유 이동은 루트 한 번의 갱신이며 아이템 노드를 방문하지 않는다. 출구가 막히면 뒤쪽을 압축 구간으로 지정한다. 완전 정체는 루트 검사만 수행한다. 삽입·중간 회수·조회·압축 경계 변경은 기대 O(log N)이며 노드 배열/free list를 재사용한다.
- `ConveyorTransportRun`: 소유권, 시간 진행, 월드 위치, 입출구 예약 전송, 상태 이관을 담당한다. 양 끝의 입구·출구 블록만 기존 전송과 연결한다. 입출구를 매 프레임 검사하지 않고 다음 경계 도착 시각을 예약한다.
- `Block.ConveyorTransport`: 기존 ID/gate 조회와 회수를 라인에 연결한다. 다음 도착 슬롯의 예약은 위치와 순서에서 계산한다. 정확히 한 간격을 이동한 시점에도 다음 입력이 추가 프레임을 기다리지 않도록 처리했다.
- `TerrainGenerator.ConveyorTransport`: 지원 구간을 채택·분할하고 라인별로 실행한다. 해당 구간은 기존 retry/blocker/이동/no-move 순회를 우회하며 블록별 tick과 데이터 모션 완료 heap에서도 제외한다.

렌더링은 기존 카메라 컬링과 동적 배치를 사용한다. 구간 블록을 한 번 등록하고 화면에 필요한 아이템 ID·위치를 라인에서 조회한다. 매 이동마다 전체 블록의 dirty 목록을 만들지 않는다. 렌더 비용까지 O(1)이 되는 것은 아니다.

중간 회수와 gate 변경은 라인에서 직접 처리한다. 착지 애니메이션·hold·실물 preview·일반 중간 삽입이 필요하면 상태를 보존하여 기존 backend로 이관하고 해당 블록을 상호작용 경계로 둔다. 이후 주변 지원 구간을 다시 나눈다. 이 이관은 구조/외부 사건에 따른 비용이며 매 프레임 실행하지 않는다.

저장 조회는 라인 상태에서 기존 슬롯 저장 형식과 남은 이동 경로를 생성한다. 라인 폐기·블록 재사용·설치물 변경도 위치를 보존해 이관한다. 세이브 포맷 버전은 바꾸지 않았다. loaded item 수는 기존 블록 합계와 현재 라인 합계를 합쳐 집계한다.

## 적용 확인과 범위

프로파일러의 `TerrainGenerator.TickConveyors.Transport` 및 `ConveyorTransport` 집계가 새 경로다. `ActiveConveyor` 카운터는 다음 의미다.

| 카운터 | 의미 |
|---|---|
| TransportRuns | 실행 중인 라인 소유 구간 수. 0이면 해당 장면에서 새 backend가 채택되지 않은 상태 |
| TransportItems | 라인이 소유하는 아이템 수 |
| TransportLegacyBlocks | 지원 구간과 함께 남는 기존 처리 블록 수 |
| TransportCommonMoves / TransportTreeVisits | 해당 관리 단계의 공통 이동·트리 접근 차분. 외부 조회에서 먼저 동기화한 작업은 포함되지 않을 수 있음 |
| TransportRoutedBlockWakes | 해당 프레임에 라인 알림을 범위 내 기존 블록의 직접 wake로 전달한 횟수. 큐가 이미 가진 블록의 중복 요청도 포함하며 실제 이동 횟수는 아님 |
| TransportBoundaryChecks | 운송 관리 단계에서 예약 시각이 되어 실행한 입구·출구 검사 수. 각 구간의 단순 시각 비교는 제외 |
| TransportInputAttempts / TransportOutputAttempts | 운송 관리 단계에서 실제 cached 전송 함수를 호출한 횟수. 성공 횟수가 아님. 다른 단계의 기존 블록 진입점에서 실행한 입력은 이 차분에 포함되지 않을 수 있음 |
| TransportSleepingRuns | 운송 관리 단계 종료 시 입출구 모두 다음 예약이 없는 구간 수. 빈 상태 또는 변경 이벤트 대기이며 네트워크 sleep 수와 다름 |
| TransportRebuilds | 운송 관리 단계에서 비활성 소유 구간 또는 실제 프록시 바인딩 변경으로 라인을 해제한 횟수. 최초 생성과 일반 라인 캐시 전체 폐기는 별도 |

첫 지원 범위는 4블록 이상 이어진 비순환 1F 직선 중 동일 속도·동일 경로 간격의 데이터 아이템 구간이다. 양 끝은 포트이며 내부 2블록 이상부터 라인이 소유한다. 코너·분배기·2F·순환·상이한 속도·특수 모션은 기존 경계로 남는다. 유효한 간격으로 가져올 수 없는 기존 상태는 강제로 덮어쓰지 않는다. 지원 구간이 없는 라인은 간격을 두고 다시 채택을 시도한다.

밀집 라인의 float 월드 좌표 반올림 때문에 간격이 미세하게 짧아질 수 있어, 최초 이관에서만 최대 1mm의 간격 오차를 보정한다. 더 큰 실제 겹침은 기존 소유권으로 남기는 검사를 포함했다.

생성·분할·폐기에는 구간 길이에 비례하는 작업이 남고 라인 노드 저장소의 메모리 비용이 추가된다. 표시 비용은 화면에 보이는 아이템 수에 영향을 받는다. 이번 검사는 Unity import/IL2CPP, 실제 세이브 파일 왕복, Shader/Physics/Tween, 로봇팔 전체 프레임 순서나 실제 FPS를 검증한 것은 아니다. **공통 이동과 실제 운반 경로 연결은 구현했으며, 실제 FPS 효과는 엔진 실행 측정 전까지 확정하지 않는다.**

## 05:07 실측 피드백 이후 큐 수정

사용자 스냅샷은 72프레임에서 전체 프레임 13.631ms, 컨베이어 틱 5.186ms, 그중 기존 wake 큐 5.042ms, 새 운송 관리 구간 0.097ms를 보고했다. 부모·자식 시간은 중복 합산하지 않는다. 라인 소유 아이템은 로드된 583개 중 101개(17.3%)였다. 동일 조건의 변경 전 자료가 없어 FPS 개선율을 계산할 수 없으며, 소유권 도입만으로 기존 큐 병목을 해결하지 못한 상태였다.

이번 후속 변경은 다음과 같다.

- 매 프레임 모든 구간의 입구·출구를 직접 큐에 넣던 두 호출을 제거했다. 입력 성공 시 기존 adapter가 입구를 갱신한다. 출력 성공 시에는 출구의 데이터 모션·활성·렌더 등록을 명시적으로 갱신한다. 출력 성공이 없으면 이 갱신을 하지 않는다.
- 라인 알림을 받은 모든 기존 블록으로 퍼뜨리던 코드를 제거했다. 기존 블록 목록 대신 정렬된 라인 슬롯 번호를 저장하고, 이진 검색으로 알림 범위에 해당하는 슬롯만 전달한다.
- 소유 라인도 해당 프레임 처리 집합에 등록한다. 같은 프레임의 후속 알림은 기존 지연 큐에 범위를 합쳐 다음 프레임에 전달한다. 나중에 다른 출구에서 발생한 이벤트를 버리지 않는다.
- `TransportRoutedBlockWakes`를 추가했다. 기존 `Process Wake Queue`, `LineWakesProcessed`, `DuplicateFrameTicksSkipped`와 함께 잔여 큐 부하를 확인할 수 있다.

이 큐 수정 단계까지는 구간당 입출구 전송 가능 여부의 상수 개 확인을 매 프레임 수행했다. 이후 아래의 예약 처리로 교체했다. 지원 가능한 라인 형태의 범위는 확대하지 않았다.

실제 큐 메서드를 연결한 하네스에서 빈 라인 100틱의 직접 블록 처리는 제거한 포트 호출 정책 재현 시 200회, 현재 코드에서 0회였다. 완전 정체 100틱도 0회였다. 중간 회수에 따른 입구 재개, 양방향 70개 아이템의 FIFO·수량 보존, 출구 막힘 해제, 유휴 후 재공급, 좁은 범위 알림, 같은 프레임의 범위 이월, 분할 구간의 국소 전달을 통과했다. 이 비교는 제거한 포트 호출 정책만 재현하며 전체 이전 버전과 비교한 프레임 시간은 아니다.

후속 수정 후 ConveyorTransport(저장소 11,041,204개 / 연결·큐 17,742개), ConveyorLineCache(5,854개), ConveyorWakeOptimization(25,682개), ConveyorStraightTransfer(73,556개/458개 전송)를 실행해 통과했다. Unity 참조를 사용하는 Roslyn Editor/Player 구성도 오류 없이 컴파일했다. 게임 엔진은 실행·조작하지 않았으며 실측 5.042ms가 얼마나 감소했는지는 동일 조건의 새 스냅샷에서 확인해야 한다.

## 경계 도착 시각 예약

05:27 스냅샷에서도 큐 5.397ms, 운송 관리 0.369ms로 실측 개선이 확인되지 않았고, 사용자가 등속 라인의 경계 처리를 특정 도착 시각에만 수행하도록 요청했다. 이에 입구·출구 각각의 다음 처리 시각을 라인이 저장하도록 변경했다.

- 내부 공통 이동은 기존대로 구간별 갱신한다. 관리 루프는 구간 수에 비례하는 시각 비교를 유지하지만, 예약 시각 전에는 포트 상태 조회·cached 전송 함수를 호출하지 않는다. 전체 프레임 또는 전체 스케줄러가 O(1)이라는 의미는 아니다.
- 출력은 `(라인 끝 - 선두 위치) × 간격 / 속도`로 예약한다. 입력은 후미가 입구 예약 슬롯을 비우는 시각과 기존 입구 아이템의 모션 완료·hold 만료 시각에 맞춘다. 간격 0.5, 속도 1인 연속 공급은 0.5초마다 입력하며 큰 빈 간격은 실제 다음 도착까지 기다린다.
- 빈 입구와 막힌 출구는 무한대 시각으로 대기한다. 슬롯 변경·모션 착지·hold 변경 이벤트가 예약을 갱신한다. 블록의 기존 진입 경로도 `TryScheduledInput`을 사용하여 예약 전의 중복 경계 검사를 우회한다. 같은 프레임의 이동 제한으로 거절될 입력은 다음 시간 진행 때 재검사하도록 예약한다.
- 삽입·회수는 필요한 예약을 다시 계산한다. 선두 회수는 제거한 아이템의 출력 예약을 취소한다. 소유권 폐기 시 포트의 구간 참조를 해제한다. 포트 구조 변경과 Inspector 속도 편집도 연결 구간을 해제하고 다음 구축에서 새 등속 구간의 예약을 계산한다. 별도의 런타임 속도 변경 API는 추가하지 않았다.
- 무관한 프록시 생성·해제로 전역 버전이 바뀌었을 때는 실제 바인딩을 검사하고, 같은 블록이면 소유권과 예약을 유지한다. 따라서 전역 버전 변경만으로 아이템 전체를 내보내고 다시 가져오지 않는다. 실제 바인딩 검사에는 해당 이벤트 때 구간 길이에 비례하는 비용이 남는다.
- 점유·렌더 버전의 `Time.frameCount` 가산을 제거했다. 공통 이동이나 데이터 변경이 없는 정체 상태는 버전이 유지된다. 소유권 해제 시 공유 revision을 기존 블록 버전에 한 번 반영하여 새 구간이 이전 실패 캐시 버전을 재사용하지 않도록 한다.

실제 예약/포트 연결 코드를 사용하는 하네스에서 120Hz × 10초의 빈 상태는 초기 검사 이후 경계 검사 0회, 완전 정체는 최초 출력 실패 1회 이후 반복 경계 검사 0회였다. 0.5초 입력 간격, 선두 도착, 성긴 간격, 출구 빈칸 이벤트, 중간·선두 회수, 모션 도착·hold, 같은 프레임 제한, 유휴 후 재공급, 정체 버전 유지, 프록시 변경과 속도·포트 구조 변경을 확인했다. 연결·큐·예약 17,777개 단언과 저장소 11,041,204개 단언을 통과했다. 기존 LineCache/WakeOptimization/StraightTransfer/Placement 하네스 및 Roslyn Editor/Player 구성도 통과했다.

이 변경은 기존에 채택 가능한 **라인 소유 구간**에 적용된다. 코너·분기·특수 모션 등 기존 backend 전체의 반복 처리는 이번에 제거한 것이 아니다. 엔진은 실행하지 않았으므로 실제 FPS와 전체 wake 큐 시간은 새 측정이 필요하다. 새 `TransportBoundaryChecks`, `TransportInputAttempts`, `TransportOutputAttempts`, `TransportSleepingRuns`, `TransportRebuilds`로 예약 동작과 잔여 재구축을 구분할 수 있다.
