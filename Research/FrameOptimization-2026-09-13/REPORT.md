## 먼저 바꿀 수 있는 구체적인 코드

### 1. 입출력 검사에서 활성 기계 전체 순회 제거

`InputOutputModule.cs:1332`의 TryGetRuntimeCoordinateValues는 이미 `registeredRuntimeGridCoordinates[coordinate]`를 조회한 뒤에도 `activeRuntimeModules` 전체를 다시 순회해. 좌표 하나의 허용 아이템을 물을 때 기계 전체 수에 비례하는 작업을 해.

`InputOutputModule.cs:1490`의 CanAddItemToRuntimeIoOverlapCoordinate와 `:1513`의 TryGetRuntimeIoOverlapAllowedItemIds는 allowed/output/input/energy용 HashSet을 새로 만들어. 내부의 각 TryGetRuntimeCoordinateValues도 방문 집합을 새로 만들어. 이 경로는 `:5510`의 벨트 출력 가능 검사에서 사용돼. 출력물·입력물·연료 허용 여부를 구하는 과정이 여러 차례 같은 기계 목록을 훑을 수 있어.

현재 가장 큰 개별 측정 항목인 채굴기의 출력 검사와 연결되는 직접적인 비효율이야. 개선은 다음과 같이 해.

1. 등록 좌표 인덱스를 완전하게 유지하고 실제 시뮬레이션 조회는 그 좌표의 소유자만 확인해. 전체 순회는 정상 경로에서 제거해.
2. 좌표별 허용 아이템·연료 집합 또는 비트 마스크를 설치/철거/회전/필터/레시피/자원 종류 변경 시 갱신해. 단순히 전역 scratch HashSet 하나로 치환하면 중첩 호출에서 값이 깨질 수 있어.
3. 출력 대상·수용량·현재 점유 정보 조회 결과를 같은 시도 안에서 공유해. TryResolveOutputTarget은 영역 수량, 수용량, 2회 후보 순회로 같은 좌표를 반복 확인하고 있어.
4. 생산을 시작하지 못한 대기 상태도 필요한 변경 이벤트를 구독하게 해. 이미 완성품 출력 대기의 수면 처리는 있으므로 이 경로와 통합해.

좌표 등록 누락을 전체 순회가 보완하고 있을 수 있으므로 fallback만 먼저 지우면 과거의 출력 불가/로드 후 정지 버그를 재발시킬 수 있어. 설치·복원·언로드·이동·중첩 Input/OutputArea·박스 필터·벨트 2F를 검사하면서 인덱스를 완전하게 해야 해. 탐색 순서는 좌표/설치 순번 등 안정된 키로 유지해 결정론을 보존해야 해.

채굴기 전체의 관측 비용이 약 0.63ms이므로 이것 하나로 두 배 FPS를 약속할 수는 없어. 다만 기계 수와 조회 횟수가 함께 증가하면 전체 순회 구조가 더 크게 악화되므로 공장 확장에도 효과가 있는 수정이야.

### 2. 프로파일러의 무거운 월드 조사 분리

`GameManager.cs:3202`의 CaptureSceneObjectCounts는 씬 계층 전체를 돌며 GO마다 GetComponents로 MB를 확인해. `:708`의 캐시 간격은 1초야. 현재 약 2만 GO, 4.8만 MB를 대상으로 해.

별도로 perf는 `TerrainGenerator.Conveyors.cs:4225`에서 loadedBlocks를 순회하고 `:4537`, `:4563`, `:4597`에서 Transform/Renderer/Collider 계층을 조회해. 자원 호스트 중복은 제거하지만 다른 공용 prototype/host의 카운터 중복 여부는 별도 확인이 필요해. 벨트 Transform 카운터를 실제 씬의 서로 다른 GO 수로 해석하면 안 돼.

FPS/UPS/큐 길이/시간 통계는 가벼운 요청으로 유지하고, GO/MB·컴포넌트 전체 조사는 별도 수동 새로고침 또는 점진 수집으로 옮기는 게 좋아. 기존 GO/MB 표시 기능은 유지하되 매초 전체 계층을 다시 읽지 않도록 해야 해. status 수집, perf 수집, JSON/Base64 직렬화의 비용 자체도 별도 계측해야 해.

### 3. 큰 FPS 상승을 위해 전체 프레임의 빈 구간을 밝혀야 해

현재 MapObjectProfiler는 모든 엔진 작업을 합산하는 CPU 프로파일러가 아니야. TerrainWorldRenderer와 ResourceBatchRenderer에는 Unity ProfilerMarker가 있지만 이 도구의 MapObject 행에는 해당 전체 시간이 없어. 엔진 렌더링·물리·Animator·UI 등도 충분히 나뉘어 있지 않아.

다음 측정은 실제 게임과 동일 장면의 CPU Timeline에서 아래 범위를 확보하는 게 우선이야.

- Main/Render 스레드와 Job 스레드의 실행·대기 시간, Unity PlayerLoop 전체.
- Behaviour Update/LateUpdate, 물리, Animator/스키닝, UI Canvas 갱신.
- TerrainWorldRenderer, 자원 배치, 벨트 본체 배치, 카메라 컬링과 렌더 제출.
- URP 카메라 렌더, 그림자, GPU 프레임 시간, Present/Job Complete 대기.
- status/perf 수집과 직렬화 시간, 프레임별 GC 할당량.

현재 화면·월드·논리 정지 상태를 유지하는 진단 토글을 이용해 렌더만, 물리만, 애니메이션만 각각 비교해야 해. 큰 범위를 찾은 뒤 그 구간 내부를 나눠야 작은 항목을 순서대로 고치고도 FPS가 안 오르는 일을 피할 수 있어.

이후 수단은 측정 결과에 따라 선택해.

| 큰 비용이 확인된 위치 | 적용할 개선 |
|---|---|
| CPU 배치 구성/컬링/행렬 준비 | 변경된 인스턴스만 갱신하고 가시 청크 캐시를 사용해. 순수 데이터의 충분히 큰 배열에 한해 Jobs/Burst를 적용해 |

개별 GameObject/MonoBehaviour 제거는 메모리와 로딩에 의미가 있지만, 수만 개의 MB가 모두 매 프레임 Update를 실행한다는 뜻은 아니야. 이번 조사에서는 GO/MB 개수만으로 현재 FPS 원인을 확정하지 않았어.

## 실행 순서와 검증 기준

1. 전체 프레임 계측과 진단 수집 분리를 먼저 진행해. 렌더 프레임 수와 UPS 틱 수를 별도 집계하고 부모/자식 시간을 중복 표시하지 않게 해.
2. 입출력의 좌표 인덱스를 보완한 뒤 전역 fallback/반복 HashSet 할당을 제거해. 채굴기 시작 대기와 출력 대기의 이벤트 구독을 정리해.
3. 전체 타임라인에서 가장 큰 남은 범위를 선택해 렌더 캐시·물리·Jobs·셰이더 중 맞는 방법을 적용해.

동일 세이브·카메라·시각·프로파일러 조건의 A/B/A 반복과 실제 프레임 p50/p95/p99를 비교해야 해. 수량 보존, 출력 재개, 필터 변경, 청크 재로드, 결정론 체크섬도 함께 통과시켜야 해. 이번 수치로 100FPS나 2배 향상을 보장하지 않았어.

## 원본과 복원 상태

원본은 조건별 `*.jsonl`, 최초 `initial-perf.json`, CPU/GPU `process-load.json`, 빌드 검증 `build-source-verification.json`에 있어. `Summarize.mjs`를 Node로 실행하면 `summary.json`을 다시 계산해.

최종 `final-status.txt`에서 hideBelts=0, hideBeltItems=0, animalAIPaused=0, simulationPaused=0, mapObjectTickProfiling=1, timePaused=0을 확인했어. 플레이어 위치와 카메라 범위는 처음과 같아. 프로파일러 간격 변경 시도는 적용되지 않았고 1,000ms를 유지했어. 게임 진행에 따른 생산·동물 이동·자원 변화는 되돌리지 않았어. 게임 소스나 실행 빌드는 이번 연구에서 수정하지 않았어.
