# Factorio 벨트 최적화 조사와 적용

2026-09-07. 기존 벨트 이동과 시설물 동작을 유지하는 범위에서 운송 라인의 반복 조회와 변하지 않은 GPU 입력의 재설정 비용을 줄였다. Factorio의 간격 기반 저장 구조 전체나 멀티스레딩을 이식한 변경은 아니다.

## 공식 자료와 현재 구조

Factorio는 연결된 벨트를 운송 라인으로 묶어 개별 벨트 간 처리 비용을 줄이고 데이터 접근을 모았다. 이 원칙을 현재 라인의 블록 참조 재사용과 직선 전송의 중복 검증 제거에 적용했다. [FFF-148: Optimizations for 0.14](https://www.factorio.com/blog/post/fff-148)

간격 방식은 아이템의 절대 위치 대신 사이 간격을 저장하고, 자유롭게 흐르는 구간의 양 끝 값과 정체 구간의 마지막 빈 간격 위치를 갱신한다. 삽입·회수와 라인 분할에는 별도 처리가 필요하다. ProjectF에 대한 적용 판단: 이미 시작 시각·기간과 GPU 공통 시간으로 위치를 계산하므로, 현재는 그 입력 배열의 반복 복사부터 줄이는 것이 동작 보존에 적합하다. [FFF-176: Belts optimization for 0.15](https://www.factorio.com/blog/post/fff-176)

Factorio의 병렬 처리는 서로 상호작용하지 않는 그룹을 사용하며, 수면 해제 요청을 결정적인 순서로 적용한다. ProjectF의 큐 순서·프레임 처리 예산·깨우기 순서를 유지해야 한다는 근거다. [FFF-364: Multithreaded belts](https://www.factorio.com/blog/post/fff-364)

현재 ProjectF에서 아이템 소유권은 블록의 슬롯에 있고, 슬롯 이동은 점유 버전·빈자리 알림·로봇팔 회수 조건·이동 프레임·모션 시간을 함께 변경한다. 라인 전체의 offset 한 번 변경으로 대체하려면 이 계약을 보존하는 조회 호환층과 경계 처리가 먼저 필요하다. 이번에는 기존 이동 본문과 알림 순서를 유지했다.

## 구현

### 1. 운송 라인의 블록 참조 재사용

`TerrainGenerator.Conveyors.cs`의 라인 조회는 슬롯 순서의 캐시를 사용한다. `BlockDataStore`가 프록시 연결 버전을 소유하고 다음 경우 증가시킨다.

- 프록시 최초 연결 또는 다른 프록시로 교체
- 프록시 제거 및 파괴된 Unity 객체의 지연 정리
- 청크 제거
- 저장소 초기화 또는 청크 크기 재설정

캐시는 저장소 소유자, 핸들과 세대, 연결 버전이 같고 프록시가 살아 있을 때만 재사용한다. `activeInHierarchy`는 매번 확인한다. 실패 결과는 재사용하지 않으므로 기존 파괴 객체 정리와 반환값까지 유지한다. 토폴로지 구성·재시도·차단 검사·이동 처리의 반복적인 저장소 검색이 줄어든다. 연결 변경은 모든 해당 저장소의 라인 캐시를 보수적으로 무효화한다.

### 2. 직선 전송 검증 통합

`CanMoveStraightConveyorDataLaneToCached`와 중복 wrapper/Core를 제거했다. 현재 라인 호출부는 단일 `TryMoveStraightConveyorDataLaneToCached`로 후보를 검사하고, 기존 Clear → 빈자리 알림 → Set → 모션 초기화 → Dirty → 이동 프레임 기록을 실행한다.

기존 게임 호출부는 사전 Can에서 실패 후보를 걸렀다. 통합 후에도 그 호출부의 실패 후보 집계는 0회, 성공 전송 집계는 1회다. 사전 검사 없이 public cached Try를 직접 호출하는 외부 코드의 실패 진단 횟수까지 보존하는 API 변경은 아니며, 현재 프로젝트에는 그 호출 형태가 없다. 아이템 소유권·이동 조건과 관련된 변화는 없다.

### 3. 변하지 않은 GPU 이동 입력 재사용

`VirtualRenderBatcher.cs`는 기존 1,023개 단위 draw마다 MaterialPropertyBlock을 재사용한다. 배치 데이터 버전·시작 인덱스·개수가 같으면 UV와 이동 시작/끝 배열을 다시 복사하거나 설정하지 않는다. 전역 모션 시간은 기존대로 갱신하므로 아이템은 계속 이동한다.

색상과 수면 표시 색은 캐시 적중 시에도 현재 재질에서 갱신한다. 아이템 추가·제거·swap-remove·배치 초기화는 데이터 버전으로 반영한다. 아이템 수가 1,023/1,024 경계를 오갈 때 할당이 반복되지 않도록 예비 draw 캐시 1개를 보관하며, 큰 축소 시에는 실제 draw 수+1개까지만 남긴다. 캐시는 버전별로 누적되지 않는다.

### 4. 불필요한 코드와 하네스 정리

런타임 및 에셋 참조가 없는 `ConveyorRunStore.cs`와 메타 파일을 제거했다. 해당 압축 저장소는 실제 슬롯 저장소에 연결되지 않았던 코드다. 또한 기존 컬링 하네스의 동물 대역에 빠져 있던 `stateTimeRemaining` 필드를 맞춰 현재 애니메이션 메서드 검증을 복구했다. 동물 런타임 코드는 변경하지 않았다.

준비 후 라인 캐시 순회와 GPU 배열 캐시 적중 경로의 관리형 할당은 0 B였다. 1,023/1,024개 경계 40회 왕복에서도 준비 후 MaterialPropertyBlock 신규 생성은 0회였다. 초기 구성, 캐시 무효화, 데이터 변경에는 기존 조회·배열 갱신 작업이 필요하다.

저장소와 전송·배치 메서드의 실제 소스를 추출하고, 변경 전 기준 메서드를 고정해 비교했다. Unity 객체·렌더 제출·월드 상호작용의 일부 경계는 테스트 대역이다. 게임 엔진이나 새 빌드를 실행하지 않았으며, 이 수치는 GPU 드라이버 내부 업로드 횟수나 실제 FPS 개선율이 아니다. 특히 성공 전송 검증 절감은 정체된 장면의 전체 비용을 없애는 변경이 아니다.

저장소 루트에서 신규 검증을 다시 실행할 수 있다.

```powershell
./Tools/ConveyorLineCacheHarness/Run.ps1
./Tools/ConveyorStraightTransferHarness/Run.ps1
./Tools/ConveyorBatchPropertyHarness/Run.ps1
```

독립 컴파일은 기존 Unity 참조 목록을 사용하되 제거한 소스를 제외했다. 이번 검증의 응답 파일과 로그는 `%TEMP%/ProjectF-FactorioBelt-Compile/`에 있다. Unity Editor 전용 스크립트 전체 컴파일이나 IL2CPP 빌드 검증을 뜻하지 않는다.

현재 실행 중인 빌드는 변경 전 코드다. 실제 효과는 새 빌드에서 동일 세이브·카메라·프로파일러 조건으로 비교해야 한다. 중간 아이템 제거, 정체 후 재개, T자/2F 합류, 분배기 순서, 로봇팔 착지 직후 이동과 청크 재로드를 우선 확인한다.
