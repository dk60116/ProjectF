# Tick과 GameObject 완전 분리: 5단계 구현 계획

작성일: 2026-09-14

## 목표와 완료 정의

전체 공정의 상태와 Tick은 시야·청크·GameObject 생명주기와 독립적으로 유지해. GameObject는 상태를 표시하고 사용자 입력을 명령으로 전달하는 역할만 맡아. 모든 표현 객체가 없어도 같은 입력과 같은 Tick 수에 대해 같은 공정 결과가 나와야 해.

범위는 컨베이어, 파이프, 로봇팔, 생산·채굴·보관·전력, 철도·차량, 자원·농지·동물 등 영속 월드 시뮬레이션이야. 카메라·UI·애니메이션 갱신은 표현 계층에 남겨. 플레이어 입력과 물리 상호작용은 명시적인 입력 경계를 통해 시뮬레이션으로 전달해. 원거리 차량·동물·아이템의 진행을 Collider나 애니메이션 완료 콜백에 맡기면 완료로 인정하지 않아.

Unity 실행부의 얇은 드라이버가 시뮬레이션 시간을 전달하는 것은 허용해. 핵심은 드라이버 없이도 하네스에서 `Step`을 호출할 수 있고, 개별 표현 객체의 생성·파괴가 상태의 생성·파괴를 뜻하지 않는 거야. JobSystem 병렬화는 독립적인 후속 최적화이고, 이 계획의 완료 조건은 먼저 단일 스레드에서도 독립 실행이 되는 거야.

## 현재 코드에서 확인한 출발점

- `MapObjectTickManager.cs`: 고정 시간, SimulationId, Plan/Apply, 실행 주기 관리가 이미 있어. 별도 스케줄러를 추가하기보다 엔진 비의존 실행부를 추출해.
- `TerrainGenerator.ConveyorJobs.cs`: Job 노드 키가 `(Block, lane)`이야. Job 연산이 데이터 기반이어도 토폴로지 구성·결과 반영은 여전히 Block에 묶여 있어.
- `Block.SimulationState.cs`: 추출된 상태가 있지만 BlockHandle과 표현 관련 상태가 섞여 있어. 의미가 같은 저장소를 더 만들기 전에 소유권부터 정리해.
- `RobotArmWorld.cs`: 개별 팔의 엔티티화가 진행됐지만 월드 자체가 MonoBehaviour이고 OnEnable/OnDisable이 Tick 등록을 제어해. 시뮬레이션과 렌더링도 함께 있어.
- `InputOutputModule.cs`: Tick 등록이 `isActiveAndEnabled`에 의존하고, OnDisable에서 등록과 좌표 색인을 해제해.
- `TerrainGenerator.ChunkPersistence.cs`: 청크 복원이 전용 월드 등록과 설치물 Instantiate를 수행해. 저장 데이터 등록과 시각 청크 생성이 같은 경로에 있어.
- `Vehicle/Train.cs`: 위치·방향과 Rigidbody 접근이 있어. 원거리 운행을 유지하려면 운행 상태와 물리 표현의 경계를 정의해야 해.

## 공통 설계 원칙

- **상태 원본은 하나**: 실행 중 수량·진행률·에너지·연결은 시뮬레이션 저장소가 소유해. View와 저장 DTO는 원본을 중복 소유하지 않아.
- **ID는 표현과 독립**: 기존 SimulationId·영속 ID·핸들을 조사해 하나의 매핑 규약으로 통합해. 새 ID 체계를 중복 추가하지 않아. 런타임 핸들은 슬롯 재사용을 구분하고 저장은 안정적인 영속 ID로 해.
- **생성·삭제는 명령**: 설치·철거·레시피 변경·인벤토리 이동은 Tick 경계에서 적용해. View 풀 반환, OnDisable, OnDestroy는 시뮬레이션 엔티티를 삭제하지 않아.
- **Unity 의존은 경계에**: 핵심 상태·Tick에서 GameObject, Component, Transform, Unity 객체 검색, 프레임 시간, Tween 콜백을 제거해. ItemDefinition asset과 제작 트리 바이너리는 기존 원본 규칙을 유지하고, 부트스트랩에서 읽기 전용 실행 정의로 변환해.
- **실행 의미 보존**: 기존 고정 시간, 정렬, Plan/Apply, 경합 처리, 수면·깨움 규칙을 먼저 유지해. 시스템을 종류별로 묶으면서 Tick 순서를 임의로 바꾸지 않아.
- **단계별 단일 실행자**: 미이전 시스템에만 임시 어댑터를 허용해. 이전된 기능은 새 코어만 상태를 변경하고 기존 Tick·중복 필드를 같은 단계에서 제거해. 비교 실행은 하네스의 독립 월드에서만 해.
- **할당 억제**: Tick마다 LINQ·전체 상태 복사·임시 List를 만들지 않아. View에는 변경 목록이나 재사용 버퍼로 상태를 전달해.

## 1단계 — 독립 시뮬레이션 기반과 비교 하네스

**목표:** GameObject 없이 월드를 만들고 시간을 진행할 수 있는 실행 기반을 마련해.

작업:

- 전체 Tick 구현뿐 아니라 Update/FixedUpdate, 코루틴, Invoke, Tween 완료, 물리 콜백에서 영속 상태를 바꾸는 경로까지 목록화해. 시스템별 상태 소유자와 GameObject 참조를 기록해.
- `MapObjectTickManager`의 시간·정렬·Plan/Apply 실행부를 순수 C# 코어로 추출하고 MonoBehaviour는 시간 전달과 프로파일 표시만 맡겨.
- 월드 수명, 영속 ID, 좌표·점유 색인, 명령 큐, 읽기 전용 정의, 변경 알림 계약을 정해. 인벤토리·전력·유체 등 시스템 간 접근 계약도 이 단계에서 정의해.
- 기존 데이터 슬롯과 VirtualObjectWorld/BlockStateStore의 역할을 정리해. 실행 상태·조회 색인·저장 DTO 사이의 복제와 권한을 명시해.
- 코어 namespace와 작은 asmdef 경계를 마련해. 기존 Assembly-CSharp 타입을 코어에서 역참조하지 않도록 DTO와 인터페이스를 먼저 옮겨.
- 기존 하네스와 Slot2를 기준 자료로 삼아 Tick 결과와 로딩 구간별 계측 기준을 준비해. Slot2 기준 자료는 읽기 전용으로 보존해.

**완료 조건:** Unity 씬 없이 코어를 생성·Step·해제할 수 있어. 같은 명령과 Tick 수로 반복 실행한 상태가 일치하고, 일시정지·실행 주기·Plan/Apply 순서가 기존 규약과 같아. 아직 이전하지 않은 시스템이 남았다는 범위도 명확해야 해.

**정리 대상:** 중복 스케줄러, 중복 ID, 이전된 코어에 남은 Component 생존 검사와 프레임 시간 참조를 제거해.

## 2단계 — Block에서 물류 시뮬레이션 분리

**목표:** 컨베이어·파이프·로봇팔이 시각 Block 없이 물건과 유체를 전달하게 해.

작업:

- 컨베이어 노드를 엔티티/좌표/레인 핸들로 전환해. 연결 구성, 이동 중 아이템 소유권, 분배 커서, 픽업 예약, 수면·깨움 상태를 코어가 소유하게 해.
- 기존 BeltSimulationJob과 버퍼를 재사용하고 Block을 통한 입력 캡처·결과 반영·이웃 조회를 데이터 저장소 접근으로 교체해. 코너, 2F 교차, 분배기 상태도 포함해.
- PipeWorld의 유체 상태·연결과 렌더링을 분리하고, 설비와 연결되는 유체 포트 계약을 사용해.
- RobotArmWorld의 팔 실행 상태·대상 조회·Plan/Apply를 분리해. 전력·인벤토리·레인·차량 화물 접근은 1단계 계약을 따르게 해. 미이전 설비 연결은 한정된 어댑터로 유지해.
- 청크 생성 없이 전체 물류 레코드를 등록하고, 모든 엔티티 등록 이후 연결을 일괄 복원해. 표현 객체의 결합은 멱등적으로 처리해 중복 등록을 막아.

**완료 조건:** 표현 객체가 없는 벨트·팔·컨테이너 테스트 공정과 파이프 테스트망이 여러 청크를 가로질러 동작해. 전체 표시/일부 표시/표시 없음에서 운송 결과와 수량이 일치해. 합류·루프·막힘·분배·잡기 경합·유체량·뷰 재결합 회귀를 통과해.

**활용할 하네스:** ConveyorTransportHarness, ConveyorBatchPropertyHarness, RobotArmIoHarness, RobotArmBeltPickupHarness, PipeFlowHarness 등 실제 로직을 검증하는 기존 항목부터 연결해.

**정리 대상:** 이전된 Block 물류 상태·Tick·연결 캐시와 월드 렌더러의 Tick 등록 경로를 제거해. 렌더링 편의용 상태가 아이템 소유권을 결정하지 않게 해.

## 3단계 — 생산·채굴·인벤토리·전력 분리

**목표:** 일반 공장의 생산과 물류가 모두 표현 객체 없이 연속 실행되게 해.

작업:

- InputOutputModule 공통 상태와 IO 처리를 코어로 옮겨. 레시피, 투입·배출, 연료, 진행률, 정지 원인, 예약, 재고 변경의 소유권을 일원화해.
- 생산기·용광로·채굴기·보일러·펌프·발전기·탱크·상자 등 실제 파생 타입을 1단계 목록과 대조하며 이전해.
- 전봇대 연결, 전력 공급·소비 배분과 로봇팔 전력 조회를 전역 데이터망으로 전환해. 비표시 전력망도 동일하게 계산해.
- 자원 잔량과 채굴 대상 조회를 시각 리소스·Block에서 분리해. 물·지형 속성처럼 원거리 공정에 필요한 값도 좌표 기반 데이터로 조회해.
- 설치·철거·회전·설정 변경을 명령으로 처리하고, 관련 연결·수면·깨움만 갱신해. UI는 엔티티 상태를 읽고 변경 명령을 보내게 해.

**완료 조건:** 원거리 채굴 → 벨트/팔 → 생산 → 보관과 물 → 보일러 → 발전 → 소비 공정을 표현 객체 없이 실행해. 같은 입력에서 재고·생산 횟수·진행률·전력 배분이 기준과 일치해. 재료 부족, 출력 막힘, 전력 부족과 복구가 정상이어야 해.

**정리 대상:** 이전된 InputOutputModule의 활성 상태 기반 Tick 등록, GameObject 좌표 레지스트리, Transform 기반 공정 조회, 중복 인벤토리와 진행률을 제거해.

## 4단계 — 철도·차량과 나머지 월드 시뮬레이션 분리

**목표:** 원거리 운행·환경 변화까지 포함해 영속 월드에서 GameObject 의존 Tick을 없애.

작업:

- 철도 연결과 운행 위치를 선로 ID·진행 거리·방향 등 데이터로 표현해. 차량 연결, 정차, 적재·하역, 노선과 점유·충돌 규칙을 코어로 옮겨.
- 차량 Transform·Rigidbody는 코어 상태의 표현과 명시적인 외부 입력 연결을 담당하게 해. 시야 밖에서도 적용할 이동·충돌 규칙을 데이터로 구현하고, 기존 물리 기반 동작과 달라지는 부분은 기준 시나리오로 검증해.
- 자원 성장·고갈, 농지·비료·파종, 동물 이동·섭식·성장, 월드 시간 등 남은 영속 상태 변경을 이전해. 필요한 공간 조회와 이동 가능 정보도 청크 View와 독립시켜.
- 플레이어 상호작용·충돌 입력의 기록 가능한 경계를 정해. 효과음·애니메이션·Tween 완료로 생산이나 운송을 확정하는 경로를 제거해.
- 1단계 의존 목록을 다시 검사하고 어댑터 및 미이전 Tick 수가 0인지 확인해.

**완료 조건:** 원거리 열차가 근거리와 원거리 공장 사이를 운행하고 화물을 교환해. 뷰 제거·재생성 중 열차 위치, 화물, 농지·동물 상태가 유지돼. 모든 월드 View를 제거해도 전체 시뮬레이션 하네스가 진행돼.

**정리 대상:** 남은 MonoBehaviour 기반 영속 Tick, OnEnable/OnDisable 등록, 임시 시스템 어댑터, 시각·물리 콜백에 묶인 상태 확정 경로를 제거해.

## 5단계 — 전체 시뮬레이션 로드와 근거리 View 로드 분리

**목표:** Slot2 전체 공장을 복원하면서 지형·시각 오브젝트 Initialize를 근거리로 제한해.

작업:

- 로드를 `읽기·파싱 → 전체 엔티티/상태 등록 → ID 참조·연결 복원 → 실행 버퍼 구성 → 근거리 View 결합`으로 전환해. 참조 대상이 전부 등록되기 전에 연결 복원을 시작하지 않아.
- 초기 월드 준비 조건을 전체 시뮬레이션 복원과 플레이에 필요한 근거리 표현 완료로 정의해. 월드가 준비되기 전에 일부 설비만 먼저 Tick되지 않게 해.
- 저장 DTO를 Tick 경계의 일관된 스냅샷에서 생성해. Job 완료와 명령 적용 시점을 맞추고 이동 중 아이템, 예약, 대기 순서, 시계·난수 등 다음 Tick을 결정하는 상태까지 보존해.
- 파일 직렬화·압축은 스냅샷 이후 처리하고 런타임 저장소를 동시에 읽거나 변경하지 않게 해. 기존 비동기 저장 경로를 재사용해.
- BlockStateStore의 실행 상태 복제와 GameObject 전역 검색을 정리하고, 저장 상태 원본을 시뮬레이션 저장소로 통합해. 탐험 기록과 View 활성 청크 목록의 의미도 분리해.
- View 생성은 거리 우선·프레임 예산으로 처리하고 청크당 무조건 한 프레임 대기를 제거해. View 언로드는 시뮬레이션 엔티티와 연결을 그대로 유지해.
- 포맷이 바뀌면 버전을 명시해. 비교용 Slot2는 별도 읽기/변환 경로로 사용하고 원본을 덮어쓰지 않아. 계속 지원할 필요가 없는 이전 포맷의 런타임 분기는 남기지 않아.

**완료 조건:** Slot2 전체 11,320개 설치물 상태를 복원하고, 기존 설정에서 초기 시각 청크는 플레이어 반경 약 289개로 제한해. 안전 여유·경계 표현 때문에 달라지는 개수는 별도 기록해. 원거리 공정도 즉시 같은 규칙으로 실행돼.

**최종 검증:**

- 동일 초기 상태와 기록된 입력으로 N Tick 진행한 뒤, 전체 표시/근거리 표시/표시 없음의 정규화 상태를 비교해. 정수·ID·재고는 정확히 비교하고 부동소수 비교 허용치는 필드별로 사전 정의해.
- 생산·소비가 있는 공정은 단순 총량 보존 대신 생산/소비 장부를 포함해 누락·복제를 검사해.
- `연속 N+M Tick`과 `N Tick → 저장 → 새 월드 로드 → M Tick`의 결과를 비교해.
- 시각 청크를 반복 생성·해제해도 엔티티 수, 연결, 예약과 Tick 등록 수가 변하지 않아야 해.
- 로드 중에는 입력을 고정하고, 실제 게임 검증은 같은 머신·빌드·세이브 조건으로 파싱, 상태 등록, 연결, 버퍼, View 생성, 준비 완료, 저장 캡처, 파일 쓰기, 메모리, GC, 씬 정리 시간을 나누어 측정해.
- 성능 완료 기준은 원거리 View 생성이 준비 완료의 선행 조건에서 빠지는 것이야. 총 로딩 초 단위 목표는 1단계의 런타임 기준 계측 후 확정하고 측정 전 단축률을 보장하지 않아.

## 단계 진행 규칙

1 → 2 → 3 → 4 → 5 순서로 진행해. 각 단계의 완료 조건을 통과한 시스템만 이전 완료로 표시하고, 전체 월드를 근거리 청크만으로 여는 변경은 5단계에서 적용해. 일반 공장 무표시 검증은 3단계, 전체 월드 무표시 검증은 4단계, Slot2 Save/Load 성능 검증은 5단계가 기준점이야.

이 문서는 구현 기획이야. 이번 작업에서는 런타임 코드를 변경하거나 Unity/게임을 실행하지 않았어. 기존 하네스 이름은 재사용 후보이고 각 단계에서 실제 코어를 검증하는지 확인해야 해.
