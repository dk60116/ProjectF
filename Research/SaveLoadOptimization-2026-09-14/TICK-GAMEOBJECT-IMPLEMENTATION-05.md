# Tick / GameObject 분리 — 5단계 진행 기록

작성일: 2026-09-14

## 현재 상태

**5단계의 로드 준비 상태 관리, 청크 시간 예산 처리, 저장 경계와 파일 교체를 구현했어. 전체 시뮬레이션 로드와 근거리 View 로드의 완전 분리는 아직 아니야.**

앞 단계의 인벤토리/채굴/전력 연결, 철도/화물, 개별 동물 등에는 GameObject 의존성이 남아 있어. 현재 저장된 전체 청크의 복원 범위와 순서는 유지했고, 원거리 청크를 생략하거나 언로드하는 기능은 켜지 않았어. 이번 결과를 1~5단계 전체 완료나 Slot2 로딩 시간 문제 해결로 해석하면 안 돼.

## 적용한 변경

### 1. 최종 복원이 성공해야만 준비 완료

- 엔진 비의존 `WorldRestoreProgress`로 Records, Chunks, Connections, Checkpoint, Ready, Failed 단계를 구분했어.
- TerrainGenerator의 기존 `worldReadyForPresentation`과 `pendingWorldFinalization`은 독립 bool 저장소 대신 이 단계에서 읽는 값으로 바꿨어. 별도 준비 완료 플래그를 중복 추가하지 않았어.
- 로드 시작 시 준비 상태를 먼저 닫고, 기존 농지/동물/BlockStateStore 레코드 적용 후 청크 생성을 시작해. 레코드 등록 자체가 모든 시스템의 독립 실행 부트스트랩으로 바뀐 것은 아니야.
- 모든 청크 처리가 끝난 뒤 기존 연결/컨베이어 아이템/런타임 등록을 복원하고, 벨트 체크포인트와 플레이어 탑승·인벤토리·올가미 복원 콜백까지 성공해야 Ready가 돼.
- 이전에는 Ready를 설정한 다음 외부 복원 콜백을 호출했어. 이 순서를 고쳐 콜백 실패 후 불완전한 월드가 실행되는 경로를 막았어.
- 레코드/연결/체크포인트 오류, 청크 생성/정리 오류, 호스트 비활성화로 중단된 로드는 Failed로 남아. 생성 결과가 빈 월드여도 무기한 대기하지 않고 오류를 남겨.
- `WorldLoadingPhase`, `WorldLoadingError`를 조회할 수 있어. 진행률 100%는 최종 성공 전에는 표시하지 않아. 오류 복구 UI를 새로 만든 것은 아니야.

### 2. 무조건 청크당 한 프레임 대기 제거

- TerrainChunkStreamingScheduler가 같은 프레임에 사용한 시간을 공유해. 예산이 남아 있으면 다음 청크를 같은 프레임에서 처리해.
- 초기 월드 복원에는 새 설정 `initialWorldLoadFrameBudgetMilliseconds`를 적용하고 기본값은 8ms야. 초기 복원은 설치물 개수 제한 대신 시간 예산으로 나눠 처리해. 일반 이동 중 스트리밍은 기존 단계별 개수 제한도 유지해.
- 초기 복원 중 예산이 남아 있으면 표면 생성/메시 복사 Job을 같은 프레임에 Complete해서 다음 단계로 진행해. 예산이 소진됐거나 일반 스트리밍이면 기존 Job 대기 yield를 사용해. 여러 청크 Job을 동시에 실행하는 구현은 아니야.
- 8ms는 엄격한 상한이 아니야. 한 번의 Instantiate, 등록/정리, Job Complete나 메시 업로드가 오래 걸리면 그 작업은 예산을 넘을 수 있어. 최종 연결 복원과 DTO 등록 전체를 시간 분할한 것도 아니야.
- 코루틴 취소 시 보유 IEnumerator를 직접 Dispose해. 코루틴 드라이버가 자동 정리한다고 가정하지 않아. 성공/실패/취소의 정리 경로도 하나로 모았어.
- 실패한 청크는 완료 개수에 넣지 않고, 코루틴 및 활성 청크 추적이 남아서 재시도를 막지 않도록 정리해. 실패 뒤 남은 큐는 명시적인 새 로드/취소에서 비워.

이전 Slot2 분석의 ‘청크마다 반드시 한 프레임’이라는 대기 하한을 만드는 코드 경로는 제거했어. 실제 Slot2가 몇 초 빨라졌는지는 측정하지 않았어.

### 3. 저장 체크포인트 경계

- SaveManager.IsLoading이 파일 읽기/씬 전환뿐 아니라 월드 복원 단계도 포함해. 완료 기록도 최종 외부 복원이 끝난 시점으로 옮겼어.
- 플레이 중 월드가 아직 준비되지 않았거나 청크 처리가 진행 중이면 저장을 거부해. 저장 요청 후 한 프레임 사이 상태가 바뀌는 경우도 캡처 직전에 다시 검사해.
- SimulationTickWorld의 `CanCaptureCheckpoint`는 Tick 실행 중 또는 미적용 명령이 있는 상태를 거부해. 현재 저장 DTO가 명령 큐를 보존하지 않으므로 조용히 명령을 누락시키지 않도록 했어. 저장 때문에 임의로 Tick을 추가 실행하지 않아.
- 벨트 토폴로지/대기 쓰기 반영과 빈 레인 체크포인트 캡처를 map DTO보다 먼저 수행해. 점유 레인과 빈 레인이 서로 다른 준비 상태에서 수집되지 않게 순서를 바꿨어.
- 상태 수집은 기존처럼 메인 스레드에서 yield 없이 진행하고, 분리된 DTO의 압축/파일 쓰기는 기존 Task 경로를 재사용해. 상태 수집 자체의 긴 정지 시간을 없앤 것은 아니야.

### 4. 기존 슬롯을 먼저 삭제하지 않는 저장

- 목적 파일과 같은 디렉터리의 고유 임시 파일에 전체 압축 데이터를 기록하고 flush한 뒤 교체해.
- 기존 슬롯은 File.Replace, 첫 저장은 File.Move를 사용해. 기존 File.Delete → File.Move 경로와 공용 고정 `.tmp` 이름을 제거했어.
- 직렬화 실패나 대상 파일 잠금으로 교체가 실패해도 이전 슬롯을 보존해. 이번 작업이 만든 임시 파일만 finally에서 정리해.
- 바이너리 포맷과 버전 62는 그대로야. 백업 이력이나 모든 파일시스템/전원 장애에 대한 복구 보장을 추가한 것은 아니야.

## 검증

Unity 에디터·게임·PC UI는 실행하거나 조작하지 않았어. 실제 SaveSlot2 파일도 변경하지 않았어.

| 검사 | 결과 |
| --- | --- |
| 순수 코어 .NET Standard 2.1 빌드 | 경고 0 / 오류 0 |
| Assembly-CSharp 보충 참조 빌드 | 경고 113 / 오류 0 |
| WorldPersistenceHarness | 52개 통과 |
| SimulationCoreHarness | 244개 통과 |
| AnimalAIOptimizationHarness | 68개 통과 |
| BeltJobsHarness | 3,087개 통과 |
| SplitterSaveHarness | 설치물 직렬화 왕복 240개 및 기존 체크포인트 바이트 비교 통과 |
| 실제 압축 파일 생성/교체/읽기 | 게임 DTO 내용과 다음 체크포인트 유지 확인 |
| CheckBoundaries | 코어 엔진 비의존 및 4개 월드 수명 계약 통과 |

WorldPersistenceHarness는 실제 스케줄러/복원 상태 및 추출한 Terrain/SaveManager/파일 교체 코드를 실행해. Unity 코루틴/시간/작업량과 토폴로지/플레이어/DTO는 테스트 대역이야. 가상 시간의 2ms 청크 10개를 5ms 예산에서 3/3/3/1개씩 처리하는 검사는 게임 성능 실측이 아니야.

파일 실패 검사는 별도 Windows 임시 파일만 사용했어. 실제 게임 직렬화기와 DTO를 쓰는 SplitterSaveHarness도 별도 임시 파일로 압축 저장 생성·교체·로드 후 데이터 일치를 확인했어. 실제 씬의 생성/파괴, Job safety/Burst, Slot2 초기화·캡처·저장 전체 시간과 원거리 공정 결과는 검증하지 않았어.

## 남은 완료 조건

1. 앞 단계에서 남은 시스템별 상태 소유권과 데이터 IO/토폴로지 복원을 완료해야 해.
2. 현재 BlockStateStore 등록 뒤에도 필요한 전체 청크 GameObject 생성을 제거하고, 순수 실행 버퍼를 전체 월드에서 구성해야 해.
3. 실제 공장의 전체/근거리/무표시 결과, View 재결합, N Tick → 저장/로드 → M Tick 결과 비교가 필요해. 기존 디스크 DTO에 없는 명령/시계 제어/일부 예약 상태도 명시적으로 처리해야 해.
4. 그 뒤에만 근거리 View 생성·언로드와 거리 우선 로드를 적용할 수 있어. 현재 전체 청크 목록을 반경으로 잘라서는 안 돼.
5. 허용된 Unity 런타임 검증에서 Slot2의 파싱, 레코드 등록, 연결, 버퍼, View 생성, 준비 완료, 저장 캡처, 파일 쓰기, 메모리/GC를 같은 조건으로 측정해야 해.
